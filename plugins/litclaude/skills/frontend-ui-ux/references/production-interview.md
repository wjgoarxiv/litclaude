# From a design request to a working screen

Choose the output mode from the user's actual request. A critique or plan is read-only. A build with a clear target proceeds to source changes and inspection. A bare skill name with several frontends needs a target choice; naming a skill does not settle scope. PostToolUse guidance is a reminder to inspect the changed UI, never permission to redesign unrelated screens.

Before implementation, record a short direction and the finite routes, controls and states that matter. Read current components, brand tokens and dirty files. Preserve established identity in brownfield work. For new work with no visual direction in the brief, apply the authored default pixel profile without asking; absence of direction is not an unresolved choice. The profile is not a mandate to recolor an existing product.

There is no mandatory interview. Ask only when two plausible answers would materially change scope, architecture, permissions, accessibility, or visual direction. Resolve a known conflict before installing tooling or producing a baseline capture; a capture is not needed to ask the question. Ask one high-impact question at a time, present concrete alternatives and their consequences, then wait for the answer before choosing the next unresolved material decision. Continue for as many rounds as materially necessary; there is no fixed question count.

If the brief itself names competing directions and says both directions are acceptable, acceptance alone is not a selection or delegation: that visual axis remains unresolved. This is different from a brief that gives no visual direction at all. Ask about the competing directions as their own round after higher-impact questions have been answered. You may include a recommendation in a concrete alternatives question, but do not treat that recommendation as a selection or begin work on the unresolved direction before the user selects or delegates it. Apply the same rule to any other material axis the brief leaves undecided. Give each remaining open axis its own round after higher-impact choices have been answered. A default is valid only when the brief settles that axis, expressly delegates it to you (for example, “your call” or “pick one”), or the alternatives would not materially change the result.

Retain earlier answers across rounds in the conversation and task-local direction note. On resume, reread the confirmed choices and inspect partial work before asking anything new; do not re-ask a resolved question. When all material choices have been answered or delegated, state the default and proceed only on remaining details that do not materially change the result. A skill name or keyword-only request does not authorize a build: review, plan, and keyword-only requests remain read-only. An answer resolves the stated design choice; it does not grant broader file, host, permission, credential, or publication authority.

The beta2 contract records the real inventory, tokens, responsive transformations and acceptance criteria as they develop. It can evolve with the code. Validate it before acceptance using the helper rooted at the selected installed skill directory. A validator result proves schema consistency, not an attractive or working interface. Do not stop after handing over a contract when the user requested a screen.

Use deliberate type hierarchy, one coherent palette and an original crisp pixel illustration tied to the product's purpose. A smooth generic icon does not satisfy the pixel direction. Compose separate mobile line breaks; use Korean display leading above Latin display leading. Keep readable body text and comfortable controls. Effects stay behind content. Prefer an asymmetric layout that still gives the primary task an obvious reading order.

Exercise the actual page: initial empty state, successful primary action, validation error and recovery, keyboard focus, responsive layout and reduced motion. Check 320, 390 and 1440 CSS pixels. A class that sets display can override the hidden attribute; include a targeted `[hidden] { display: none }` rule and verify the transition in the browser. Record unavailable browser capability separately from implementation completion; never substitute source inspection for rendered evidence.
