# Bounded README production interview

Claude Code loads this reference through the selected `readme-studio` skill. There is no mandatory interview. Ask only when two plausible answers would materially change scope, architecture, permissions, accessibility, or visual direction. README examples include a conflict over audience or purpose, incompatible content scope, a static versus motion delivery that changes accessibility or package contents, or an unresolved authorized output location.

When the brief says both directions are acceptable but does not choose or hand that choice to you, the direction remains unresolved; agreement that either is acceptable does not select one. Apply this rule to every material axis the brief leaves open. Ask one high-impact question at a time, beginning with the most consequential choice; bring each remaining material choice into its own round after higher-impact questions have been answered. Continue for as many rounds as materially necessary, with no fixed question count. Do not announce a default or produce the affected work for an unresolved choice before the user answers. A default is allowed only when the brief has settled that axis, explicitly delegates it (for example, “your call” or “pick one”), or the alternatives would not materially change the result.

Once the material questions have answers, state the default and proceed only on details that are settled, delegated, or immaterial to the result. Use repository facts, applicable instructions, established identity, and earlier answers to support those details; do not pause for ceremonial approval of ordinary reversible work. Do not combine unrelated questions into a questionnaire.

Retain earlier answers across rounds in the conversation and task-local direction note. On resume, reread confirmed choices and inspect partial work before asking anything new. Do not re-ask a resolved question. An answer narrows the current task; it does not grant broader file, host, permission, credential, network, or publication authority. Review, plan, and keyword-only requests remain read-only.
